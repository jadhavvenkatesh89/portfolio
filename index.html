CASE 01

Metadata-Driven Ingestion — the Process Control Framework

Problem
Every new data source meant a new hand-built pipeline. With sources as varied as on-prem SQL Server, Oracle, SharePoint, Dataverse, Salesforce, Synapse and the Cornerstone (RAU) API, development was slow, patterns diverged between engineers, and maintenance scaled linearly with source count. Nothing could answer a simple operational question — what ran last night, what did it load, and did it finish?
Architecture — PCF
A Process Control Framework: three metadata tables that describe the entire platform, and generic ADF pipelines that execute whatever those tables say. No source has its own pipeline. Onboarding is a set of metadata rows, not a deployment.

Generic pipelines
Three master pipelines move data across the layers, each reading its instructions from PCF: mpl_S2L_Main (Source → Landing), mpl_L2C_Main (Landing → Curated) and mpl_C2P_Main (Curated → Processed). A master looks up its batch in Process, then a Switch on proc_type dispatches each object to the child pipeline that knows how to handle that source type — an on-prem database, a SaaS platform, a document library or a REST API. Adding a source platform means adding one child pipeline and a metadata row; adding a table means only the row. ADF orchestrates but does not transform: extracts land as Parquet in ADLS, and L2C and C2P invoke Databricks jobs that do the work and write managed Delta tables — keeping transformation logic in version-controlled notebooks rather than inside pipeline definitions.
Transformation & history
The Curated layer is a faithful, typed, de-duplicated representation of source rather than a modelling layer — scd_type2_ind is N throughout, so loads are Type 1: latest value wins and no history is retained. Table_Columns carries the source-to-target column mapping and ordering, which is what lets one generic pipeline load any object without knowing its shape at design time.
Validation built into the framework
Every process carries its own proc_executable and val_executable, so correctness travels with the definition rather than living in a separate test suite. The validation notebook compares source and target counts, and checks for duplicates and anomalous row-count movement, per object per run. Each execution is stamped into Process with its start and end time — giving a complete, queryable history of what ran, what it loaded, and whether it passed.
Serving layer
Consumers never read Processed tables directly. The serving layer is a set of one-to-one views in Databricks SQL over them — no transformation, no logic — which decouples Power BI datasets and Copilot Studio agents from physical table changes underneath. The view is the contract; the table is free to be refactored.
Identity & access
No credentials live in a pipeline. Secrets are held in Azure Key Vault, Azure-to-Azure authentication runs on managed identity so there is no key to rotate or leak, and a self-hosted integration runtime gives the cloud platform reach into on-prem SQL Server and Oracle without opening those networks outward.
Orchestration
Control-M owns scheduling, not ADF. A Control-M job triggers Data Factory with a single parameter — batch_name — and the framework resolves everything else from Process: which objects belong to that batch, what type each is, what executes it and what validates it. Scheduling and dependency management stay in the enterprise scheduler where operations can see them; job failure raises an alert by email through Control-M, so the platform does not rely on someone watching a pipeline monitor.
My role — PCF 1.0 → 2.0
I adopted an existing framework and extended it, which meant every change had to land without breaking loads already running on it. Three additions defined 2.0: PROC_SKIP_IND, a one-shot skip — set it to Y and the next run of that process is bypassed, after which the framework resets it to N itself, so a deliberate one-off exclusion can never silently become permanent. PROC_ON_ICE_IND, its deliberate counterpart — Y holds a process out of every run until someone explicitly turns it back on, for a source that is decommissioned, embargoed or mid-remediation. And ADB_JOB_CLUSTER_SIZE, which moved cluster selection into metadata and opened the path to serverless compute, improving execution efficiency without touching a single pipeline. I also brought the SaaS and API estate onto the same contract as the relational sources.
Scale & operations
Incremental loads driven by overwrite_ind keep daily volume bounded rather than re-copying history. Landing paths are partitioned by source and date so downstream reads prune. API and SaaS sources bring their own constraints — token lifetime, pagination, rate and API limits on Salesforce and Cornerstone — handled generically with paged retrieval and retry with backoff rather than per-source code. Because dispatch is by proc_type at batch level, one failing feed degrades a batch rather than stopping the platform — and the 2.0 control flags mean a problem source can be taken out of tonight's run, or held out indefinitely, by updating a row rather than editing a schedule. With ADB_JOB_CLUSTER_SIZE on serverless, compute is matched to the process rather than to the batch, so a small load no longer waits on a cluster sized for the largest one.
Decisions & trade-offs — why two skip flags, not one A single "disabled" flag would have covered both cases in half the code. Rejected — the two situations fail in opposite directions. A temporary exclusion that someone forgets to re-enable silently starves a downstream report for weeks; a permanent hold that resets itself re-admits a source that was deliberately taken out. Making the one-shot skip self-clearing and the indefinite hold manual-only means each flag's failure mode is the safe one. The cost is a second column and a rule to explain — cheap against a feed that quietly stops loading.
Decisions & trade-offs — framework vs. templates Considered per-source pipelines built from a shared template repo — the conventional answer, and easier to debug one source at a time. Rejected — template drift across engineers is invisible until something breaks in production, and a seven-source estate becomes seven divergent codebases within a year. PCF makes every object's configuration auditable in one place and moves the change surface from deployment to data. The cost is real: the framework becomes a single point of failure, and a wrong config row fails in a generic pipeline where the stack trace tells you little. That is why metadata is validated before execution and every run is recorded in Process — the audit trail is what makes a generic framework debuggable.
What I'd do differently Version the PCF tables in a config repo promoted by a release step, rather than editing them in place. Metadata is code once it drives execution — and a production table with no change history tells you what the config is, never who changed it or why. I'd also expose Process as a run-history dashboard from day one instead of querying it during incidents, and revisit the blanket scd_type2_ind = N: Type 1 everywhere is the right default, but it means any question that starts "what did this look like last quarter" cannot be answered from Curated at all.
Outcome: new-source onboarding reduced from [X days] to [X hours] across 7+ source platforms and [X tables], with three master pipelines to maintain instead of one per source — and a complete, queryable execution history for every load.

CASE 02

On-Prem SQL Server → Azure Lakehouse Migration

Problem
Years of business logic lived inside on-premises SQL Server as stored procedures, views and tables — undocumented, tightly coupled, and only executable on a server the organisation wanted to retire. A lift-and-shift to Azure SQL would have moved the problem without solving it; the logic itself had to be re-expressed in a platform that scales.
Architecture
A three-track migration. Tables were re-landed through the metadata-driven ingestion framework into Delta and re-modelled as managed tables in Databricks, with data types, keys and constraints mapped rather than assumed. Views became Databricks SQL views over the curated layer, preserving the consumer-facing contract so downstream reports did not have to change on day one. Stored procedures — procedural T-SQL with temp tables, cursors and control flow — were decomposed into PySpark / Spark SQL notebooks, rewritten as set-based, idempotent transformations rather than translated line by line, then orchestrated as jobs in place of SQL Agent.
My role
Led the migration end to end: inventoried and dependency-mapped the estate, set the conversion patterns the team executed against, rewrote the complex procedural logic myself, and owned the cutover decision — including what did not get migrated.
Validation & cutover
Correctness was proven, not assumed. Every migrated object was reconciled against its on-prem counterpart on row counts and on control totals for each measure, both systems ran in parallel for [X weeks], and the business formally signed off through UAT before consumers were switched over. Scope: 70+ objects across stored procedures, views and tables.
Decisions & trade-offs Considered a like-for-like lift to Azure SQL Managed Instance, where the procedures would have run essentially unchanged. Rejected — it is faster and cheaper up front, and it carries every existing limitation into the new platform: no lakehouse scale, no Delta lineage, no path to the analytics layer being built alongside it. Rewriting is the slower option and the one that leaves you somewhere worth being. The trade-off is real risk during conversion, which is why reconciliation was treated as a first-class deliverable rather than a testing afterthought.
What I'd do differently Retire aggressively during the inventory instead of after. A meaningful share of any legacy estate is dead logic serving a report nobody opens — migrating it converts an on-prem maintenance burden into a cloud one at full price. Prove consumption first, migrate second.
Outcome: 70+ procedures, views and tables migrated off on-premises SQL Server and rebuilt on Databricks — signed off through business UAT, [X%] reduction in batch runtime, and business logic now versioned in Git rather than living only inside a database.

CASE 03

Medallion Lakehouse on Azure Databricks

Problem
Structured and unstructured data landed in one undifferentiated pool. No lineage, no consistent quality gate, and analytical queries that scanned far more than they needed.
Architecture
A Medallion design on Delta Lake, named for what each layer does: Landing preserves raw fidelity; Curated applies schema enforcement, de-duplication and conformance in PySpark; Processed holds business-ready aggregates that serve the BI layer directly. Delta transaction logs give time travel and traceable lineage at every hop.
My role
Architected the layer contracts, wrote the PySpark and Spark SQL transformations, and tuned jobs for large-scale transformation and load into downstream analytics.
Scale & cost
Z-ORDER on the high-cardinality join keys and a scheduled OPTIMIZE keep the small-file count bounded — the difference between a Processed-layer query that scans a partition and one that scans the lake. Curated is partitioned on ingest date; clusters are autoscaled and job-scoped rather than always-on, so idle compute is not billed.
Decisions & trade-offs Considered collapsing Landing and Curated into a single cleansed layer to save storage and one hop of compute. Rejected — once raw fidelity is gone you cannot replay a transformation bug, and every quality rule you later tighten becomes unbackfillable. Storage is the cheapest thing in the architecture; irreversibility is the most expensive.
What I'd do differently Define the layer contracts as enforced schemas from day one rather than by convention. Where the Curated shape is only documented, drift arrives quietly and is discovered downstream in a dashboard rather than upstream in a job.
Outcome: measurable gains in data quality and lineage traceability, with downstream query performance improved by [X%] on [named workload].

CASE 04

Secure Executive BI & Reporting Layer

Problem
Business units needed the same dashboards but must never see each other's numbers, and operational reporting ran on a separate, manually managed stack.
Architecture
A Power BI semantic model over the curated layer with advanced DAX measures and calculated columns, secured by Row-Level Security roles so each stakeholder group sees only its own slice. Scheduled SSRS deployments cover the pixel-perfect operational reporting that sits alongside it.
My role
Built the DAX model and RLS roles, owned SSRS deployment, scheduling and maintenance across multiple business units, and acted as the single point of contact between business users and the technical team.
Scale & operations
Star-schema model with narrow fact tables and pre-aggregated Processed-layer measures, so the report layer does arithmetic rather than joins. Incremental refresh on the largest fact keeps refresh windows flat as history grows.
Decisions & trade-offs Considered separate workspaces and a separate model per business unit — the simplest way to guarantee isolation. Rejected — it multiplies every future measure change by the number of business units and guarantees the definitions diverge. One model with RLS roles keeps a single definition of each metric; the trade-off is that the security model now has to be tested, so role membership is verified against a known matrix before each release.
What I'd do differently Push more business logic out of DAX and into the Processed layer. Measures that encode joins or filters are invisible to anyone outside Power BI, and a metric definition living only in a semantic model is a governance gap, not a feature.
Outcome: secure self-service for [X stakeholder groups], with report refresh reduced from [X] to [X].

CASE 05

Data Quality & Observability Framework

Problem
Bad data was being discovered by business users in a dashboard, days after it landed. Quality checks existed, but as ad-hoc assertions scattered inside individual notebooks — invisible, inconsistent, and impossible to report on.
Architecture
A declarative validation layer sitting between the Curated and Processed layers. Rules — nullability, value ranges, referential integrity, row-count deltas, freshness SLAs — are defined as configuration against a dataset, not as code inside a job. Failing records are quarantined to a side Delta table with the rule that rejected them rather than failing the run, so a single bad batch degrades a feed instead of stopping the platform. Every execution writes a quality-score row that feeds a Power BI observability dashboard.
My role
Designed the rule schema and the quarantine contract, implemented the PySpark evaluation engine and the score model, and built the monitoring dashboard on top.
Scale & operations
Rules evaluate in a single pass over the batch, so cost scales with data volume and not with rule count. Freshness breaches and score drops alert before the business sees the dashboard.
Decisions & trade-offs Considered fail-fast: abort the pipeline the moment any expectation breaks. Rejected — in a multi-source platform that converts one publisher's bad day into a platform-wide outage. Quarantine-and-continue keeps good data flowing and makes the failure measurable; the trade-off is that the Processed layer can now be quietly incomplete, so completeness is itself a published metric rather than an assumption.
What I'd do differently Version the rule definitions alongside the data contract they defend. A rule tightened on Tuesday silently changes what Monday's score meant, and a quality trend you cannot interpret is worse than no trend at all.
Outcome: quality issues surfaced [X hours] earlier — at ingestion rather than in a dashboard — across [X datasets] under continuous monitoring.

CASE 06

Lakehouse Cost & Performance Optimisation

Problem
Compute spend was growing faster than data volume — the signal that a platform is paying for inefficiency, not for scale. Nobody could attribute cost to a workload, so nobody could reduce it.
Architecture
Baseline first: tagged jobs and clusters to attribute spend per workload, then profiled the worst offenders in the Spark UI. Three classes of fix followed — layout (partition strategy revisited, OPTIMIZE and Z-ORDER to kill small-file overhead), compute (right-sized autoscaling job clusters replacing oversized all-purpose ones, aggressive auto-termination), and query (broadcast joins for small dimensions, predicate pushdown, caching only what is genuinely re-read).
My role
Owned the profiling, proposed the change set with projected savings per item, and implemented and measured each one against the baseline.
Scale & cost
Every change is reported as a before/after pair — runtime and DBU — so the saving is demonstrable rather than asserted.
Decisions & trade-offs Considered simply scaling clusters down until spend hit target. Rejected — that trades cost for SLA breaches and hides the real problem, which was data layout rather than compute size. Fixing layout first meant the smaller clusters were sufficient rather than merely cheaper. The trade-off is that OPTIMIZE itself costs compute, so it runs on a cadence tuned per table instead of nightly everywhere.
What I'd do differently Instrument cost attribution from day one instead of retrofitting it. Half the effort in this work went into establishing what was actually being spent where — a question the platform should be able to answer continuously, not during an optimisation drive.
Outcome: [X%] reduction in compute spend on [named workload], with runtime down from [X min] to [X min] and no SLA regression.

CASE 07

Conversational Agents over Curated Data

Problem
Answering routine business questions meant raising a report request and waiting. The data already existed in the Processed layer — the bottleneck was access, not engineering.
Architecture
Agents built in Microsoft Copilot Studio, grounded on curated sources rather than on the raw lake: topics map user intent to defined actions, and Power Automate flows act as the execution layer reaching into the governed data and the systems behind it. Because the agent sits on the Processed layer and not on raw Landing data, every answer inherits the quality rules and the security model already enforced upstream.
My role
Designed the grounding strategy and topic/action model, built the agents and their supporting flows, and defined what the agent is permitted to answer.
Scope & guardrails
Agents answer from governed sources only, with an explicit fallback to a human when a question falls outside scope — a wrong confident answer costs more trust than no answer. Deployed to [channels: Teams / web] for [X user group].
Decisions & trade-offs Considered pointing the agent directly at source systems and raw tables for maximum coverage. Rejected — an agent grounded on ungoverned data inherits none of the quality or row-level security work and will confidently surface numbers the business has already agreed are wrong. Grounding on the curated layer narrows what the agent can answer; that narrowing is the feature, not the limitation.
What I'd do differently Instrument unanswered and deflected questions from the start. The queries an agent cannot handle are the highest-value backlog a data team can have, and they are lost unless you capture them deliberately.
Outcome: self-service answers to [X routine request types], removing [X hrs/week] of manual reporting turnaround.
